# DBaaS v2 — plan and progress

Rewrite of the DBaaS plugin on top of `nacl/4.23`, keeping the UI and replacing
the provisioning internals. Tick items as they land; every unchecked box is
still open work.

Base: fresh clone of `paratpanu18/cloudstack`, branch `nacl/4.23`, working
branch `panabordee/dbaas-v2`.
Predecessor: `panabordee/dbaas-full` in `~/cloudstack-ui-src` (4.22 line), whose
retired code is preserved on a backup branch — see §7.

## 1. What changes and what does not

| Layer | v1 (4.22) | v2 |
| --- | --- | --- |
| UI | wizard, Database section, Show Password, Create/Reset dialogs | **kept, ported as-is**, extended for the new fields |
| API commands | createDatabase, getDatabasePassword, resetDatabasePassword, listDbaasEngines, deleteDbaasCredentials | kept, plus list/delete credentials and a report-back endpoint |
| Credential storage | `dbaas_credentials`, encrypted with `DBEncryptionUtil` | kept, plus `status` / `status_message` |
| Transport into the instance | SSH from the management server (paramiko, forced command, allowlist) | **config drive + cloud-init**, then an in-VM agent |
| VM login password | our own `vmaccess.sh`, shown once, unrecoverable | **CloudStack native** password-enabled template + `resetPasswordForVirtualMachine` |
| DB password | always generated by the management server | generated in the instance by default, or supplied by the user |

The point of the rewrite: the management server never needs a route to the
instance. Provisioning survives a broken virtual router, a wrong network choice
and an unreachable guest network — the failure modes that produced most of v1's
defects.

## 2. Design decisions (settled)

- **Config drive, not the VR metadata service.** User data arrives as a virtual
  CD-ROM, so it works when DHCP/the VR is broken. The network offering must
  list ConfigDrive as its UserData **and** Password provider.
- **VM password is CloudStack's, not ours.** A password-enabled template gets a
  random password per deploy and `resetPasswordForVirtualMachine` regenerates
  it. With ConfigDrive as the password provider this works without the VR.
  Consequence: the tenant cannot choose their own VM password (no such API);
  they can reset it as often as they like.
- **DB password may be chosen by the tenant**, generated when left empty. A
  supplied password means `requestHasSensitiveInfo = true` on the command and
  no string interpolation into SQL.
- **Status is recorded, not inferred.** Show Password stops guessing between
  "still provisioning" and "failed".

- [x] Spike: is there a VM lifecycle hook that removes the need for the UI to
      clean up credentials and data disks itself? **Not a usable one.**
      `VirtualMachineManager.Topics.VM_LIFECYCLE_STATE` exists and plugins do
      subscribe to it (`DnsProviderManagerImpl.configure()`), but 4.23 only
      publishes on it from two call sites in `UserVmManagerImpl`: `Destroyed`
      (:3767) and `Running` (:5560). Expunge sets the state without
      publishing, so a subscriber waiting for `Expunging` never fires, and
      acting on `Destroyed` would delete the credentials and data disks of an
      instance the tenant can still recover. Superseded by the sweeper below.
- [x] Credential/data-disk cleanup after expunge. Corrected premise: 4.23's
      `publishVmLifecycleMessageBus` only publishes **Destroyed** and
      **Running** (2 call sites) — no Expunging publish exists, and deleting
      on Destroyed would wipe credentials of recoverable instances. Instead:
      a sweeper in `DbaasManagerImpl` (interval `dbaas.credentials.cleanup.interval`,
      default 3600s) deletes credential rows of expunged instances with the
      documented join and **logs** orphaned DATADISK volumes (count + size,
      no auto-delete — tenant data, no human confirmation = too risky). The
      UI's expunge-time cleanup stays as the explicit path.

### Phase B — config-drive provisioning (new-instance flow)

- [ ] Per-engine first-boot script baked into the template: read the config
      drive, configure the engine, report the result
- [ ] `provision_mode` (`configdrive` | `ssh`) per engine in `config.json`,
      exposed through `listDbaasEngines` as `provisionmode`
- [ ] `createDatabase`: build the user data document, attach it to the stopped
      instance, store the credential, start the instance, return immediately
- [ ] Wizard deploys with `startvm=false` when the engine reports `configdrive`
- [ ] Template rebuild: mysql first, `passwordenabled=true`
- [ ] Acceptance: deploy onto a network the management server cannot reach,
      with the VR down, and still get a working database and a visible password

### Phase C — status and report-back

- [ ] `status` / `status_message` written by the plugin (`pending` at create)
- [ ] Report-back endpoint validated by a one-time token: bound to one instance
      UUID, single use, TTL, stored hashed, rate limited, every call logged
- [ ] Instance reports `confirmed` / `failed` with a reason
- [ ] Show Password renders the real status; the polling guesswork is deleted
- [ ] Decision recorded: the endpoint accepts an unauthenticated caller (the
      instance holds no CloudStack credentials) — accepted or rejected

### Phase D — in-VM agent, retire SSH

- [ ] Agent in the template polls its config source for pending jobs
- [ ] Create Database on a running instance goes through the agent
- [ ] Reset Database Password goes through the agent
- [ ] Remaining engines rebuilt: mariadb, postgresql, mongodb
- [ ] Delete the SSH transport: `cs_api.py`, `extension.py`, paramiko, the
      retry loop, `PROVISION_ATTEMPTS`, `TRANSIENT_CONNECT_ERRORS`, the budget
      calculation, `provision.sh` and its allowlist, the forced-command key,
      `sudoers.d-dbaas-provisioner`, `ssh_connect_timeout_seconds`,
      `dbaas.provision.timeout`, the transient-error list in `utils/dbaas.js`

### Phase E — additions worth having

- [ ] `@ActionEvent` on create / reset / show, so credential access is audited
- [ ] `listDatabaseCredentials` + a picker in Show Password (today only the most
      recent credential per instance is reachable)
- [ ] Delete database / drop user, on the instance and in the table
- [ ] Engine health in the Database list, reported by the agent (never probed
      from the management server — that would reintroduce the dependency)
- [ ] Connection hint for isolated networks: the connect command uses the guest
      IP, which is unreachable from outside without a port forward
- [ ] Idempotency key on create, so a retry cannot half-create a second user
- [ ] Clear the user data once the instance reports `confirmed`, so the DB
      password does not sit in CloudStack's database in cleartext

### Out of scope (recorded, not planned)

Backup/restore of tenant databases, TLS for database connections, DBaaS-specific
resource limits (VM limits apply today), multi-NIC instances (`cs_api.py` picks
the first NIC).

## 4. Known issues carried over from v1

- Deploying a database on an instance that already has one fails hard on
  "user already exists" — correct, but the UI could say so more clearly
- `storeCredential` inserts a new row per create/reset; only the latest is read
- Data disks and credential rows are only cleaned up by the UI's destroy path;
  the lifecycle-hook item in Phase A replaces it

## 5. Sequencing

A → B → C → D, with E folded in wherever it is cheapest. Phase B alone removes
the network dependency from the flow that fails today; C makes failures legible;
D deletes the old transport for good.

## 6. Testing

Each phase carries its own acceptance line above. Beyond those:

- deploy on a healthy shared network — the baseline that already works
- deploy on an isolated network with no route from the management server
- deploy with the VR stopped
- create a database on an instance that already has one
- reset a database password, then connect with the new one
- destroy with and without expunge; confirm data disks and credential rows
